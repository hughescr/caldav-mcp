# caldav-mcp

A small remote MCP server that lets Claude clients read, create, change and delete events in Apple iCloud calendars over CalDAV. It runs on AWS Lambda behind CloudFront, so it does not depend on a laptop being awake. It copies the security and deployment approach of [wildduck-mcp](https://github.com/hughescr/wildduck-mcp).

## Status

Version 1.2.1 is released at https://caldav-mcp.rungie.com. It has eight tools: the five read tools `list_calendars`, `list_events`, `search_events`, `get_event` and `get_event_attachment_download`, and the three write tools `create_event`, `update_event` and `delete_event`. It has four scopes (`calendar:read`, `calendar:write`, `calendar:delete`, `calendar:invite`). The sign-in page lets the user choose which requested permissions to grant (write and delete are ticked by default, invite is not), and a completed consent replaces what that client was allowed before. A recurring event in a named timezone that has an edited or moved occurrence is fully readable: iCloud sends the edited occurrence's `RECURRENCE-ID` with its `TZID` instead of in UTC, and the server reads that form with an `occ2_` occurrence token. When the queried window holds only a deleted occurrence of a repeating event and that occurrence lies in the requested range, `list_events` and `search_events` report that series in `series_without_occurrences` instead of calling it unreadable or failing the calendar. The published output schemas give field names and basic types only and never forbid additional fields, so a client holding older tool definitions accepts replies with new fields. Tool descriptions, the server instructions and input field descriptions say only what an agent needs before it acts: errors and unusual situations are explained in the response when they occur, by the error message or by the result's `notes`. The download result carries the link once in its text content and once in `structuredContent`, with no separate `resource_link` block. `get_event` and the write tools handle `travel_time`. The probe is at version 0.6.0. The first deployment was version 0.1.1 on 2026-11-11. The owner connected it from a Claude client and reported that `list_calendars` worked. This was not checked independently from server logs.

An event's `resource_href` is an opaque string issued by iCloud. The server never decodes or re-encodes the event's name (the last segment of the path) and sends it back byte for byte. It accepts the calendar's own path plus one name made of the characters a URI path allows unchanged and `%XX` escapes in either case, such as `%3A` or a double-encoded slash `%252F`. It refuses `.` and `..` (also after one decoding, such as `%2E%2E`), escaped control characters, and a single-encoded slash or backslash (`%2F`, `%5C`, either case), the one form that a single decoding upstream would turn into a path separator. A refused href from a client is `invalid_input`, and nothing is sent to iCloud. If iCloud names one event by an address the server refuses, that event is one `unreadable` entry (`resource_href: null`, reason `unsupported_resource_address`) and the rest of its calendar is listed. Measured on 2026-11-13 on one real account: an event created from an Apple reminder has an href with `%3A` and `%252F`. In 1.0.0 it made its whole calendar report `upstream_error` for any range near it. On the final 1.1.0 build, including the refusal of single-encoded `%2F` and `%5C`, a seven-year read of the account on 2026-11-13 answered `ok` for every calendar, listed 2,304 events, and reported 2 old repeating series, both with `RDATE`, as unreadable (`unsupported_recurrence_data`). On the 1.1.1 build, a read-only check against the same account on 2026-11-13, over the same seven years, read all calendars with 0 unreadable events and listed 2,318 events; the 2 series with `RDATE` are listed. A repeated read-only check of the 1.2.0 build against the same account on 2026-11-13 read all calendars with 0 unreadable events, over the same seven years in 360-day ranges (2,318 events) and again in 60-day ranges; for the measured range that failed in 1.1.1, every calendar answered `ok` and the series was reported once in `series_without_occurrences`. A read-only check of the 1.2.1 build against the same account on 2026-11-13 read all calendars with 0 unreadable events, over the same seven years in 360-day ranges (2,319 events) and again in 60-day ranges. For the range that showed an out-of-range `series_without_occurrences` entry in 1.2.0, every calendar answered `ok` and the result has no entry. A one-day range on the deleted occurrence's own date also has no entry, as expected: the 31-day padding brings the series' remaining occurrences into the query window, so iCloud expands the series normally and the stripped form does not arise. A read-only `GET` on 2026-11-13 showed that iCloud answers 404 for five traversal-shaped addresses that use encoded slashes to reach through another calendar, and 200 for the true address. `PUT`, `DELETE` and multiget with such names were not probed.

A series without occurrences in the queried window, measured read-only on one real account on 2026-11-13: when the window holds only a deleted (`EXDATE`) occurrence of a repeating event and no remaining one, iCloud's expanded answer returns the series itself in a stripped form: one `VEVENT` without `RECURRENCE-ID`, with `RRULE`, in a `VCALENDAR` without `VTIMEZONE`, `VERSION`, `PRODID` or `CALSCALE`. Before 1.2.0 the server reported that resource as unreadable (`unsupported_recurrence_data`), and failed the whole calendar (`upstream_error`) when no other repeating event of that calendar was readable in the window. Now it is one entry of `series_without_occurrences` when one of its stored `EXDATE` values lies in the requested range, and is left out otherwise (see "Tools"); either way the calendar status stays `ok`. Any other unexpanded series (an `RRULE`, or an `RDATE` or `EXDATE` without `RECURRENCE-ID`, in any other shape) keeps that behaviour.

The tool definitions are short. The `tools/list` result was 113,722 bytes and is 37,016 bytes (37,160 in the 2026 protocol). The descriptions total 3,519 characters and the server instructions are 2,100 characters. What the model reads on every turn (every description, every input schema and the instructions) is 14,778 bytes. Output schemas are published in `tools/list`, but, as observed in Claude Code on 2026-11-13, only a tool's name, description and input schema reach the model, so the output schemas are not part of that total. The rare-case output fields (`unreadable`, `series_without_occurrences`, `request_warnings`, `exceptions_dropped`, `exceptions_shifted`) are published as plain objects, `notes` as an array of strings and `guest_notice` as a string. Every published output schema gives field names and basic types only (with `required` for the fields always present, nullable types and the field descriptions): it never forbids additional fields and has no closed `enum` or `const`, tuple, length, item-count, pattern or numeric bound, so a client holding older tool definitions accepts a reply with a new field or value. The server still validates every result against its strict schema before sending, and the input schemas stay strict. The rules every tool shares are in the server's MCP instructions (see "Tools"), each time union and the attendee object are listed once per schema under `$defs` and referenced with local `$ref`s, and `tests/tool-budget.test.ts` caps the sizes: 1,200 characters for each description, 3,670 for all descriptions, 2,250 for the instructions, 37,480 bytes for `tools/list` (in both protocol eras) and 14,930 bytes for the model-visible total. The same test keeps the explanations of errors, result fields and rare cases out of descriptions, instructions and input field descriptions. The listed schemas are validated with the SDK's client-side validator (Ajv, JSON Schema draft 2020-12). Whether Claude clients accept the `$ref` and `$defs` form is checked only after the deploy.

After a deployment, existing connections keep working with the scopes they already have. No release since the write scopes needs a new scope. The occurrence and series edits of 1.0.0 need none: a connection that already holds `calendar:write` has the scope `update_event` needs for them, and one that holds `calendar:delete` has the scope `delete_event` needs. A connection made before the write scopes existed must reconnect the connector and tick the permissions on the sign-in page to use the write tools. A release that changes a tool's inputs or description, as 1.1.0 and 1.2.0 do for every tool, is not picked up by clients automatically, because clients cache the tool list. A client also validates replies against the output schemas it cached: on 2026-11-13 a client holding the 1.1.1 definitions rejected a 1.2.0 reply with "data must NOT have additional properties" until its tool list was refreshed. From 1.2.1 on the published output schemas never forbid additional fields, so a new reply field needs no refresh; 1.2.1 itself still needs one last refresh or reconnect, because a client keeps the older, strict output schemas until then. After deploying 1.2.1 (it needs no new scope): in claude.ai, use "refresh tools list" in the connector's settings; in Claude Code, run `/mcp` and reconnect the connector. The server accepts the new inputs at once; only the cached tool definitions are stale, and a conversation that already loaded the old definitions keeps showing them until a new conversation starts. Rolling the code back does not undo changes already made to calendars.

The write tools are `create_event` (a single or a repeating event), `update_event` and `delete_event`; see "Write tools". `update_event` changes every field of a non-repeating event; for a repeating event it changes one occurrence (`edit_scope: "this"`), an occurrence and all after it (`edit_scope: "this_and_future"`, which splits the series in two), or the whole series (`edit_scope: "all"`: its fields, its times and rule, or turning it into a single event). `delete_event` deletes a whole event or series, one occurrence, or an occurrence and all after it. ## Tools

Every tool needs the scope `calendar:read`. The five read tools change nothing: `list_calendars`, `list_events`, `search_events`, `get_event` and `get_event_attachment_download`. The three write tools (`create_event`, `update_event`, `delete_event`) are described under "Write tools".

- `list_calendars` returns each calendar that holds events: `id`, `displayName`, `components` and `color`, at most 200, with a `truncated` flag. The `id` is an opaque path that contains the account's numeric iCloud path. Pass it back unchanged.
- `list_events` returns the events in a half-open time range (`range.start` included, `range.end` not). `calendar_ids` is optional (1 to 20 ids from `list_calendars`); omit it to read every calendar that holds events. Each result has a status per calendar, so one failing calendar does not fail the call. Recurring events are returned as separate occurrences, as iCloud expands them. A repeating event with a deleted occurrence in the range and no remaining occurrence in the range or within 31 days of it is not an event of the result: it can appear as an entry of the optional `series_without_occurrences` list (see "Limits"). Cancelled events are included, with `status` `CANCELLED`. Each event has `resource_href` (the event's path exactly as iCloud issued it, which can contain percent escapes such as `%3A` or `%252F`; pass it back byte for byte), `recurrence_id` (null unless it is an occurrence; an opaque token of at most 192 characters, to pass back unchanged), `expected_version` (the ETag), `start`, `end`, `title`, `location`, a shortened `description` and the attendee count.
- `search_events` takes the same inputs plus `query` and optional `fields` (`title`, `description`, `location`). It matches literal, case-insensitive text, not a regular expression, in this server. A `series_without_occurrences` entry is included only when its series' stored title, description or location (as `fields` selects) matches.
- `get_event` takes `calendar_id` and `resource_href` from a list or search result, and `recurrence_id` for one occurrence. It returns the full event: organizer, attendees, a longer title, location and description, `travel_time` (Apple Calendar's stored travel time, such as `PT30M`, when the event has one), and metadata for every attachment of the event (file name, type, declared size, form). `expected_version` makes the call fail with `calendar_changed` if the event changed since the list. A `recurrence_id` whose occurrence iCloud's expansion does not return, because iCloud answers that window with the series alone (the stripped form above), is `not_found` with a message that the occurrence was probably deleted. `include_raw: true` adds the stored iCalendar text, unmodified, cut to a 16 KiB prefix with `raw_truncated` set when longer. That text can contain attachment links, base64 data and instructions written by whoever sent the invitation. `download_supported` on an attachment says whether `get_event_attachment_download` can serve it.
- `get_event_attachment_download` takes `calendar_id`, `resource_href` and an `attachment_ref` from `get_event`, and optionally `recurrence_id` and `expected_version`. It reads the event from iCloud again and selects the attachment itself; it never takes a URL. The result depends on the attachment's form:
  - `inline` (base64 stored in the event) and `managed` (stored by Apple): the server copies the file, at most 20 MiB, into a private S3 bucket and returns `download_url`, a presigned HTTPS link valid until `expires_at`, at most five minutes, with `filename`, `content_type`, `size` and `fetched_by_server: true`. The file is always served as a download, never shown inline. The result is `structuredContent` plus one text content block that mirrors it, so the link appears once in each. Anyone who holds the link can use it until it expires; the result's `notes` say so (a bearer credential: do not log, store or share it; the staged copy is deleted after about a day).
  - `external` (a link to another server): the server does not fetch it. It returns `url`, the link stored on the event, with `fetched_by_server: false`, and a note that the server did not fetch or check it and that what it points to is untrusted (the note does not repeat the link). A link that contains a user name or password is refused with `unsupported_attachment`.

Calendar names, event text, time zone names, file names and raw iCalendar text are untrusted data. Clients must never treat them as instructions.

The rules every tool shares are sent once per connection as the server's MCP instructions (the `instructions` of the `initialize` result, and of `server/discover` in the 2026 protocol): untrusted data, passing ids back unchanged, the time model, `expected_version`, `operation_id`, the guest rule and the scopes, and that error messages and the notes in results say what happened and what to do next. Each tool description gives only what an agent needs before it calls that tool (what it does and how to call it), plus a short untrusted-data clause and, on `update_event` and `delete_event`, a one-sentence guest warning, because a client may not show the instructions to the model. Input field descriptions follow the same rule: for example `exceptions` on `update_event` says only "Only when a refusal asks for it". Errors, result fields and rare cases (time-zone warnings, `write_outcome`, `stored_differs_from_request`, `outcome_unknown`, `calendar_changed`, the `exceptions` choice and similar) are explained in the response where they occur, never in these texts. Every client loads the whole tool list into each conversation, so `tests/tool-budget.test.ts` caps its size, the length of each description and the model-visible total (see "Status"), and fails if a description, the instructions or an input field description names such a case.

**Notes.** A result carries an optional `notes` list of fixed sentences, each from a constant in `src/calendar/notes.ts` (never built from calendar content), each at most once, in a fixed order; the key is absent when no note applies, and an ordinary successful save has none. The notes are:

- the `timezone_warning` values the result holds (`no_timezone_on_event`, `unrecognized_timezone`, `timezone_dropped_from_date`, `utc_uncertain_dst_transition`), one note per distinct value, in list, search, get and write results;
- for `list_events` and `search_events`, that all-day, floating and unrecognised-zone events have no fixed instant and are matched with a 24-hour margin, so some may lie up to 24 hours outside the range;
- for a write result: `write_outcome` `desired_state_present` (the requested state was observed in the calendar; not proof of who saved it), whose `write_outcome` is whose after a `this_and_future` split, `readback` unavailable, `stored_differs_from_request` when it lists a field (for a delete of one occurrence or the following ones, when the series read back does not show the deletion), and `exceptions_dropped` with how to restore what it lists;
- for a download result: the handling of `download_url` (a bearer credential) and, for an external attachment, that it was not fetched and is untrusted.

Errors are structured as `{ error: { code, message, request_id } }`. The message explains itself: a refusal with `edit_not_supported` says why and what to do (the `exceptions` choice and what `"drop"` removes and where it lists it, why a `"shift"` is refused, `split_at_series_start`, `count_series_needs_rrule`); `calendar_changed` for a reused `operation_id` says to reuse one only to retry the identical call; `invalid_input` with reason `rrule_until_form` says what form an `UNTIL` must have; and every `outcome_unknown` answer, on every tool and path, says that the change may or may not be saved and that the event must be got again before anything else (a test enumerates every site that produces it). The read tools forward no upstream text. A write tool's error can also carry a fixed `reason` and `field`, `differs` (the fields that differ, for `existing_resource_differs`), and `upstream`: a bounded summary of iCloud's refusal (status, content type class, at most 8 `DAV:error` precondition names taken only from a fixed list of DAV and CalDAV names, and at most 512 characters of cleaned text in which the account's id, Apple ID, app-specific password and authorization value are masked; HTML is never forwarded). The whole of `upstream` is untrusted text from iCloud.

### Write tools

The write tools create single and repeating events, update any field of a non-repeating event, change or delete one occurrence of a series or an occurrence and all after it, change a whole series (its fields, times and rule, or turn it into a single event), and delete a whole event or series. Not in 1.2.1:

- adding or changing guests (no tool has an input for attendees or an organizer);
- `exceptions: "shift"` for an all-day, floating or zoned series, or for a rule with a `BY*` part, an `UNTIL` or a frequency above weekly (use `"drop"`);
- for a series with `RDATE`: any change or delete of one occurrence or of an occurrence and all after it, and changes of times or rule (`rdate_present`); for a series with `EXRULE`: splits and changes of times or rule (`exrule_present`);
- adding or changing attachments.

The tools and their inputs:

- `create_event` takes `calendar_id`, `operation_id`, `title`, `start` and `end` (both required; iCloud refuses an event without an end), and optionally `location`, `description`, `status` (`CONFIRMED`, `TENTATIVE`), `transparency` (`OPAQUE` busy, `TRANSPARENT` free), up to 10 `alarms` (`{ before_start: "PT10M" }`, a display alarm), `recurrence` (`{ rrule: "FREQ=WEEKLY;BYDAY=TU" }`) and `travel_time`. The event's identity (its UID and resource path) is derived from the account and `operation_id`, and the event is written with `If-None-Match: *`. A retry with the same `operation_id` and the same values reports `desired_state_present` instead of making a duplicate; the same `operation_id` with different values is refused (`calendar_changed`, reason `existing_resource_differs`). Use a new random `operation_id` for each new event.
- `update_event` takes `calendar_id`, `resource_href`, `expected_version` (required) and `changes`. A field absent from `changes` is unchanged, a value replaces it and `null` removes it. A single event: every field, `start` and `end` only together (the server never computes an end), and `recurrence` makes it repeat. A repeating event needs `edit_scope`:
  - `"all"`: the change applies to the series and to every changed occurrence alike. New `start`/`end` move the series and `recurrence` replaces its rule (`null` makes it a single event); a series with changed or deleted occurrences then needs `exceptions`: `"drop"` removes them and lists them in `exceptions_dropped` (at most 50 by value, counts complete), `"shift"` moves every occurrence id and deleted date by the same UTC difference and counts them in `exceptions_shifted`, and an occurrence that sat at its own slot moves with them (a moved one keeps its times). `"shift"` works only when the old start, the new start and every exception are stored in UTC, never with a rule change (`exceptions_shift_not_utc`, `exceptions_shift_with_rule_change`), and only for a stored rule that provably moves with its start: `FREQ` up to `WEEKLY` with no part but `INTERVAL`, `COUNT` and `WKST` (`exceptions_shift_rule_not_supported` otherwise, for example a monthly rule, a `BYDAY` list or an `UNTIL`: use `"drop"` and re-apply the listed exceptions). A kept `UNTIL` that no longer fits the new start's form is `invalid_input` (`rrule_until_form`). New times or a new rule for a series with `RDATE` or `EXRULE` are refused (`rdate_present`, `exrule_present`); `"all"` without them works on such a series and keeps its `RDATE` line.
  - `"this"` with `recurrence_id`: one occurrence. A series with `RDATE` is refused (`rdate_present`). An occurrence that already has its own changes (an override) is edited in place; otherwise an override is added whose `RECURRENCE-ID` is the occurrence's slot in the series' own form, exactly as iCloud's expansion of that same version shows it (no date math). The result's `recurrence_id` is the occurrence's id from now on: an occurrence of a series with a zone name gets an `occ2_` id once it has its own changes. `recurrence` is not allowed.
  - `"this_and_future"` with `recurrence_id` and `operation_id` (required, `operation_id_required`, because the split creates a second series): the series is ended before the occurrence (`UNTIL` = its UTC instant from iCloud's expansion minus one second; a `COUNT` is replaced) and a new series, whose identity is derived from `operation_id`, starts there with the changes, taking along the changed and deleted occurrences from the split on. It is two writes, the new series first (`If-None-Match: *`) and then the original (`If-Match`); the result names the new series in `created_series` and shows it as `event`. If the second write fails, `split_incomplete` says that the new series was saved and the original was not shortened, so those occurrences show twice; repeating the same call finishes the split, and deleting the new series undoes it. A retry finishes only when the new series still holds everything the split wrote (the master's requested values, the exact deleted dates, and every carried changed occurrence line for line); if one was changed or removed since, the original is not shortened, because that would lose the occurrence from both, and the call answers `split_incomplete` (`created_series_differs`, `created_series.write_outcome: "unconfirmed"`): inspect or delete the new series. Repeating a finished split with the old `expected_version` answers `desired_state_present` only for a split that dropped its exceptions; otherwise it is `calendar_changed`, because the shortened original no longer shows what was carried. For a `COUNT` rule the new count is taken from iCloud's expansion; when that cannot be proven (an occurrence deleted before the split, a changed occurrence the expansion does not show, a series longer than the expansion window) the call needs `changes.recurrence` for the new series (`count_series_needs_rrule`). Refused: the first occurrence (`split_at_series_start`, use `all`), an occurrence of a zoned series that has its own changes (`split_at_changed_zoned_occurrence`: iCloud's text gives no UTC instant for it), a split at a moved occurrence without new `start` and `end` (`split_occurrence_changed_supply_times`), a series with `RDATE` or `EXRULE` (`rdate_present`, `exrule_present`), and new times or a new rule for the new series with changed or deleted occurrences from the split on unless `exceptions: "drop"` (`exceptions_choice_required`, with counts; a split that drops lists the dropped occurrences in `exceptions_dropped`, also in `split_incomplete` and `outcome_unknown`, where the list is cut to fit the 8 KiB error and the counts stay complete): carried unchanged, they could match no occurrence of the new series, so they are carried only when neither the time nor the rule changes. `"shift"` is always refused for a split (`exceptions_shift_not_supported_for_split`).

  A `location` change also removes Apple's map pin (`X-APPLE-STRUCTURED-LOCATION`, reported as `removed_apple_location_pin`) and keeps the travel time lines; a `description` change also removes its HTML copy (`X-ALT-DESC`). Every edited component gets new `DTSTAMP` and `LAST-MODIFIED` and `SEQUENCE` plus one; every other stored line is kept as stored.
- `delete_event` takes `calendar_id`, `resource_href` and `expected_version` (required), and `edit_scope` for a repeating event: `"all"` deletes the whole series, `"this"` with `recurrence_id` deletes one occurrence (an `EXDATE` in the series' form, and its override removed if it has one) and `"this_and_future"` with `recurrence_id` ends the series before that occurrence. Both are refused for a series with `RDATE` (`rdate_present`); `"all"` deletes such a series as any other. For those two the series stays, and the result has `deleted` (`occurrence`, `following`), the series' new `expected_version`, `readback` and `stored_differs_from_request`. An event that is gone reports `desired_state_present`.
- When iCloud answers the window of the occurrence a `recurrence_id` names with the series alone, in the stripped form described under "Status" (no occurrence in that window), the occurrence was probably deleted: `get_event`, and `update_event` and `delete_event` with `edit_scope` `"this"` or `"this_and_future"`, answer `not_found` with a message saying so (and, for a write, that nothing was saved). Nothing is sent to iCloud as a change.
- When the stored event and iCloud's expansion of it do not prove which occurrence a `recurrence_id` names (an unrecognised zone, two occurrences at the same local time in a repeated daylight-saving hour, an override that matches no occurrence, a form that differs from the series'), the call is refused with `occurrence_identity_unprovable` and nothing is sent. The server never expands a recurrence rule and never converts between zones.

Update and delete are conditional on `expected_version`, sent as `If-Match`; a different stored version is `calendar_changed` and nothing is saved. The server never repeats a write. After a 412 (iCloud refused the conditional save) or a lost or unclear answer it reads the event once. It reports `desired_state_present` when the requested state is observed; this says nothing about which call saved it. After a 412 it otherwise reports `calendar_changed`. After a lost or unclear answer it otherwise reports `outcome_unknown`: iCloud may have saved the change and rewritten some values, or another client may have changed the event since, so the agent must get the event again before doing anything else; every `outcome_unknown` message says that first. A repeated call never overwrites a newer version.

A create or update result has `write_outcome` (`applied`, or `desired_state_present`; only the latter gets a note), `readback` (`ok`, or `unavailable` when the saved event could not be read back), the new `expected_version`, `request_warnings` (`timezone_dropped_from_date`), `stored_differs_from_request` (the requested fields whose stored text differs from what was sent; iCloud rewrites some local times, for example in `Australia/Lord_Howe`; alarms are compared by their `TRIGGER` lines only; a rule is compared by its `NAME=value` parts in any order, because iCloud reorders them, with part names case-insensitive and values exact), `removed_dependent_properties`, `notes` (only when something in the result needs explaining; see "Tools") and `event`, the stored event exactly as `get_event` returns it. A delete result has `notes` too, for `desired_state_present`, an unavailable readback and a deletion of one occurrence or the following ones that the read-back series does not show. A split adds `created_series`; a series change that dropped or shifted exceptions adds `exceptions_dropped` or `exceptions_shifted`, and a split that dropped them `exceptions_dropped`. The same rule comparison decides whether a retry finds `desired_state_present`.

Times sent to a write tool: RFC 3339 text with an offset or `Z` is stored as the exact UTC instant; `{ local, zone }` is stored with that zone name as given (it is not interpreted or mapped, Windows names included, and iCloud decides; the read-back shows what it stored); `{ date }` is an all-day date, and a zone given with a date is dropped with the warning `timezone_dropped_from_date`. A time without an offset, `Z` or zone is refused. A repeating event given only an offset or `Z` is stored in UTC and keeps that UTC time, so its local time moves at daylight-saving changes; give a zone name to keep a local time.

`travel_time` (create and update; `null` on update removes it) is a duration up to `PT12H`, such as `PT30M`. The server writes `X-APPLE-TRAVEL-DURATION;VALUE=DURATION:<value>` and nothing else: no route, no travel start, no geocoding. Apple Calendar shows travel time when that line exists (measured on the owner's data). Whether it shows it on an event without an Apple map pin is not measured.

**Invitations.** The write tools have no input for attendees or an organizer, so `create_event` never invites anyone. iCloud emails guests at once when an event with attendees is created, when its time or description changes, or when it is deleted (an alarm-only or `TRANSP`-only change sent no mail), and this cannot be suppressed because iCloud ignores `SCHEDULE-AGENT` (measured 2026-11-12). So updating or deleting an event that has any `ATTENDEE` or `ORGANIZER` line anywhere in its stored text (in the series, in any occurrence, in any other component, and with or without a group prefix such as `item1.`; `X-` names do not count) also needs `calendar:invite`; without it the call is refused with `attendees_present` before anything is sent. With it, the change goes ahead, the attendee and organizer lines are never added, removed or changed, and the result carries `guests_may_be_emailed: true` with a fixed note. The server instructions and the descriptions of `update_event` and `delete_event` tell the agent to ask the user before changing or deleting an event that has guests. A new override of one occurrence and the new series of a split copy the series' stored attendee and organizer lines unchanged, because an occurrence of an event with guests keeps them (measured: a changed occurrence sends an update; a split sends an update for the shortened series and an invitation for the new one; deleting one occurrence sent no mail). This is the only place the server writes such lines, only as byte-equal copies, and only with `calendar:invite`.

Write error codes, beyond the read tools' codes: `create_conflict` (the identifier is taken elsewhere in the account), `read_only_calendar`, `forbidden` (iCloud's 403, also its answer to an end before the start), `attendees_present`, `edit_not_supported`, `write_refused` (another refusal from iCloud, with `upstream`), `outcome_unknown`, `occurrence_identity_unprovable` and `split_incomplete` (with `created_series`; an `outcome_unknown` after a split's first write also names it).

### Times

**Times you send.** Every time you send carries its timezone: an RFC 3339 timestamp with an explicit UTC offset or `Z`, for example `2026-03-08T00:00:00-08:00`. A time without an offset or `Z` is rejected with `invalid_input`, and the message says that a timezone is required. A range is at most 366 days within the years 1900 to 2100.

**Times you get.** Times are passed through as they are stored on the calendar card. A time has one of four shapes:

| Shape | Fields | Meaning |
|---|---|---|
| zoned | `local`, `zone`, optional `utc` and `offset` | Wall-clock time and the `TZID` text from the card. |
| UTC | `utc` | A true instant. |
| floating | `local`, `floating: true`, `timezone_warning` | The card has no timezone. The instant is unknown. |
| all-day | `date`, `all_day: true` | A date, not a time. It never has a timezone. The end date is exclusive. |

For a zoned time, the server adds `utc` and `offset` only when `zone` is an IANA name (such as `America/New_York`) that its runtime recognises. It does not read an embedded `VTIMEZONE` and does not map Windows zone names such as `Pacific Standard Time`; those are passed through as written, and the agent can interpret them.

`timezone_warning` is a data item, not an error. It has four values, and a result that holds one says what it means in its `notes` (one note per distinct value; the tool descriptions and server instructions do not):

- `no_timezone_on_event`: a floating time. There is no `utc` or `offset`.
- `unrecognized_timezone`: the `zone` is not recognised. There is no `utc` or `offset`, and a range result may include or miss the event because its position in time is unknown.
- `timezone_dropped_from_date`: an all-day date carried a timezone on the card. The server returned the date only.
- `utc_uncertain_dst_transition`: the local time falls in a repeated or skipped hour. `utc` and `offset` are given, but iCloud may use a different instant, up to an hour away.

Events are sorted by their stored local start time, not on one time axis. All-day and floating events up to 24 hours outside the range edges can appear in a result; a list or search result that holds an event without a fixed instant (all-day, floating or unrecognised zone) says so in a note.

### Limits

| Limit | Value |
|---|---|
| Events per result (`limit`) | default 25, at most 100 |
| Serialized response | 96 KiB (the JSON appears twice in a tool result, so fewer events may fit) |
| Calendars per call (`calendar_ids`) | at most 20 |
| Range | at most 366 days, years 1900 to 2100 |
| `query` | at most 256 characters |
| `description` in a list result | shortened to 280 characters |
| Raw iCalendar text (`include_raw`) | first 16 KiB |
| Unreadable events reported | at most 50, with a count |
| `series_without_occurrences` entries | at most 10 per result; `excluded_starts` at most 10 per entry, with `excluded_count`; `repeat_rule` at most 1,024 printable ASCII characters |
| Attachment download | 20 MiB; link valid at most five minutes; 30 seconds per call |

When a result is cut, it has `truncated: true`, the reasons (`result_limit` or `response_bytes`) and a `resume_hint`. The hint is the local start time of the last event returned. It is not a cursor: query again from that time, with an offset or `Z`, and remove duplicates by `calendar_id`, `resource_href` and `recurrence_id`. `complete` is true only when nothing was cut, no event was unreadable, every calendar was read and no `series_without_occurrences` entry was left out; entries that are listed do not affect it, and it does not prove that iCloud returned every event.

An unreadable entry has a `reason`: `malformed`, `unsupported_recurrence_data`, `resource_too_large` or `unsupported_resource_address`. The last means iCloud named the event by a path this server does not accept; that path is not repeated, so the entry has `resource_href: null` and only counts the event. The rest of its calendar is still listed.

A series with a deleted occurrence in the range and no remaining occurrence in the range or within 31 days of it can be an entry of `series_without_occurrences`, which list and search results carry only when there is one (`series_without_occurrences_truncated: true` appears when entries were left out). Each entry has `calendar` (the index into `calendars`), `resource_href`, `title`, `series_start` (the series' stored start, shaped as an event's), `repeat_rule` (the stored `RRULE` text, exactly as stored), `excluded_starts` (the stored `EXDATE` values, in stored order, at most 10) with `excluded_count` (all of them), and a fixed `note`: iCloud matched the repeating event to the range but returned no occurrence in it, usually because an occurrence in the range was deleted, and this is not an error. The server computes nothing from the rule. Because it queries beyond your range (see below), iCloud can return such a series for a deleted occurrence outside it, so an entry is listed only when at least one of its stored `EXDATE` values (all of them, not only the 10 shown) lies in the requested range. Each value is matched as an event's start is: exactly by its instant, or, for an all-day, floating or unrecognised-zone value, with the 24-hour margin, which the result's `notes` then mentions. A stripped series with no `EXDATE` at all has nothing to compare and is listed. A series left out is not an entry, not unreadable and does not affect `complete`, and only listed entries count toward the cap of 10. The calendar status stays `ok`. An entry has no `expected_version`: `get_event` on its `resource_href` (without `recurrence_id`) reads the series.

A repeating series that carries `RDATE` is listed by `list_events` and `search_events`: iCloud's expansion leaves the series' `RDATE` line on every expanded occurrence, and an expanded occurrence that has a `RECURRENCE-ID` may carry `RDATE` or `EXDATE`. The stripped form of a series without occurrences (see "Status") is reported as above. Any other unexpanded series, that is `RRULE` on any other expanded component, or `RDATE` or `EXDATE` on one without a `RECURRENCE-ID`, still makes that resource unreadable (`unsupported_recurrence_data`), and the calendar `upstream_error` when no other repeating event of it was readable in the window. A stripped series beside such a resource does not vouch for it. Occurrences are passed through as iCloud returns them; iCloud reads a floating `RDATE` value as UTC and returns one extra occurrence for it. Changes to one occurrence of such a series, or to it and all after it, are refused with `rdate_present`.

A short query can miss an occurrence that was moved more than 31 days away from its original date. iCloud returns a moved occurrence only when the query window covers both its original time and its new one, so the server queries 31 days beyond each end of your range and filters the result, events and `series_without_occurrences` entries alike, to the requested range.

## Account connection

A client discovers this server's own OAuth endpoints and opens one page at `/authorize`. That page shows the client name, the client's redirect host, two fields (Apple ID and app-specific password) and the requested permissions. Read access, when requested, is a fixed row; every other requested permission is a checkbox the user can tick or untick (see "Scopes"). It is styled by one built-in inline style block that the page's Content-Security-Policy allows by hash; the page loads no scripts or outside resources. A help link beside the password field opens Apple's article on app-specific passwords. Its one outbound link, beside the password label, opens Apple's article on creating an app-specific password (`https://support.apple.com/102654`) in a new tab without sending a referrer. There is no second consent page and no TOTP step. The form posts to `/auth/connect`.

Use an app-specific password that you create only for this connector. Apple lets you revoke each one on its own.

**The password is stored.** wildduck-mcp never stores a password. This server has to, because CalDAV has no session token. Every iCloud request sends the Apple ID and the app-specific password. The server keeps them like this:

- They are encrypted with AES-GCM, bound to the account and to this stored connection.
- The key lives in an SSM SecureString keyring, outside the database.
- They are never put in a cookie, a hidden field, a redirect or a log.
- The client only ever receives this server's own short-lived tokens.

An app-specific password is not limited to calendars. It also opens iCloud Mail and contacts. That is the weak point of this design. The mitigations are the dedicated, separately revocable password, the key held outside the database, the allowlist below and the fixed-host rule. See "Known weak point" in [docs/plan.md](docs/plan.md).

### Allowlist

Only Apple IDs you list can connect. Without it, anyone could attach their own account to this deployment.

The list is the environment variable `ALLOWED_APPLE_ID_HASHES`: account hashes separated by commas. An account hash is the base64url SHA-256 of the lower-cased Apple ID with a fixed prefix. It is a pseudonym, not a secret. Produce one with:

```sh
bun run apple-id-hash
```

The script reads the Apple ID from a prompt or from stdin, never from arguments, and prints only the hash.

An empty or missing list means nobody can connect. A malformed entry stops the server from starting. The list is checked at login before any request to Apple, at code exchange and token refresh, and on every `/mcp` request. Not being on the list, a badly formed Apple ID and a wrong password all show the same failure page.

The login throttle allows 5 attempts per account in each 15-minute window. An attempt is reserved before the request to iCloud. A wrong password keeps its attempt counted until the window ends. A successful login or a temporary iCloud failure releases it. A full window is refused without contacting iCloud.

### Scopes

The user decides on the login page which of the requested permissions the client gets. The scopes and their checkbox labels:

| Scope | On the login page | Used by |
|---|---|---|
| `calendar:read` | Fixed row "Read your calendars and events (always included)". It is the default when a client requests no scope. | every tool |
| `calendar:write` | Checkbox "Create and change events", ticked by default | `create_event`, `update_event` (with `calendar:read`) |
| `calendar:delete` | Checkbox "Delete events (whole events, single occurrences, or all following occurrences)", ticked by default | `delete_event` (with `calendar:read`) |
| `calendar:invite` | Checkbox marked SENSITIVE, "Change events that involve other people. iCloud emails them at once: invitations, updates and cancellations from your Apple Account. Has effect only together with create/change or delete.", not ticked by default | additionally `update_event` and `delete_event` on an event with attendees or an organizer, checked after the event is read (`attendees_present`) |

A checkbox appears only for a scope the client requested. The client gets read (if it asked for it) plus the boxes left ticked, and the token response's `scope` names exactly that set, which may be narrower than the request. If nothing is granted (possible only when the client did not request read), the page says "Choose at least one permission", and nothing is stored and iCloud is not contacted. A refresh can keep or narrow the granted scopes, never widen them; a narrowing applies to earlier access tokens from their next verification on. To grant more, reconnect and tick the box. Each completed consent replaces what that client (the same `client_id`) was allowed before, for that account: its earlier grants and codes stop working as soon as the user presses "Connect and allow" and iCloud accepts the password, and other clients are not affected. This holds for a second submission of the same page too (a double click or a resent form): the later submission wins, and only its code works. A client that registers again gets a new `client_id`, and its old grants then live until they expire, the password is replaced, or they are revoked (see "One consent per client" in [docs/auth-design.md](docs/auth-design.md)). A tool called without a scope it needs returns `insufficient_scope`, naming the scope and the checkbox to tick.

`calendar:write` covers creating and changing events; deleting needs `calendar:delete`. Grants are never widened: a connection made before the write scopes existed keeps only the scopes it has, and must reconnect and tick the boxes to use the write tools.

### Token lifetimes

These match wildduck-mcp. Access tokens last five minutes. Grants and connections last at most 180 days. Refresh tokens rotate; an identical retry within ten seconds gets the same response, and a replay of an old token after that revokes the client's grant. Revocation at `/revoke` ends the access and refresh tokens.

The stored password is checked against iCloud when a code is issued or exchanged and when a refresh token is used. It is not checked on each `/mcp` request. The tool call itself reaches iCloud.

If iCloud answers a tool call, or a token request, with HTTP 401, the connection is marked `reconnect_required` and the user must connect again. A temporary iCloud or network problem returns `temporarily_unavailable` and keeps the grant. A 403 from iCloud is treated as temporary by the read tools; for a write it is `read_only_calendar` or `forbidden`, since iCloud also answers 403 to event data it refuses.

Replacing the stored password ends every existing grant for that account. Each client must authorize again. Only a repeat login with the identical, still-active credential keeps existing grants, and then only those of other clients: the client that logged in again keeps only its new grant. See [docs/auth-design.md](docs/auth-design.md).

### Accepted limitations

- Allowlist membership is observable to someone probing the login endpoint.
- Anyone who knows an allowlisted Apple ID can block new connections for that account for 15 minutes at a time. Existing grants keep working. Each such attempt is a real failed sign-in at Apple.
- There is no "forget this account" function. A stored password stays sealed in the table until it is replaced or the record expires (180 days).

## Fixed upstream hosts

The login page accepts no server URL. The server sends CalDAV requests only to `caldav.icloud.com` and to hosts shaped like `pNN-caldav.icloud.com`, which iCloud's discovery returns for each account. Requests must use HTTPS on the default port with no embedded credentials. Redirects are followed at most three times, and only to hosts that pass the same rule. A stored URL is checked again after decryption, every time it is used.

The one other host is `gateway.icloud.com`, for managed attachments, and only for a `GET` without credentials or cookies. The rules are in `src/caldav/managed-attachment-policy.ts`: the `ATTACH` must carry a `MANAGED-ID`, and a link under the account's calendar home, to an `.ics` file or to a collection is never fetched. A redirect from that host is refused, not followed. Owner decision OD9 allows the credentials to be sent to an Apple download host that answers 401 with a Basic challenge, but only to a host on a separate list in that module, and that list is empty. Credentials are never sent anywhere else. Other attachment links are never fetched.

## Runtime and storage

Environment variables:

- `PUBLIC_BASE_URL`: the canonical HTTPS origin. In production it is imported from the bootstrap stack. It is never taken from the Host header.
- `AUTH_KEYRING_PARAMETER`: the SSM parameter name, `/caldav-mcp/prod/auth-keyring`.
- `CREDENTIAL_TABLE_NAME`: the DynamoDB table.
- `ALLOWED_APPLE_ID_HASHES`: the allowlist above. Empty means nobody can connect.
- `DOWNLOAD_BUCKET_NAME`: the private bucket for staged attachment copies. In production it is imported from the bootstrap stack. Unset disables staging only: inline and managed downloads fail with `temporarily_unavailable`, external links still work, and the other tools are unaffected.

Provision the keyring separately as an SSM Standard SecureString under the AWS-managed `aws/ssm` key. It is a new keyring. Never share it with wildduck-mcp. The shape is `{"activeKeyId":"v1","keys":{"v1":"<base64 of 32 random bytes>"}}`, at most four KiB. Generate the bytes in memory and send the value through stdin or API request data, not through command arguments, files or logs. CloudFormation does not create it. The runtime role can only read that one parameter. The CI deploy role is denied reading or writing its value, and is denied direct access to the table's items. It can still deploy code to the function, and that code runs with the runtime role. Anyone who can read both the keyring and the table, or who can deploy code, can decrypt stored passwords. The key is the AWS-managed `aws/ssm` key, so any principal in the account with `ssm:GetParameter` and table read can decrypt too.

To rotate, add a new key and change `activeKeyId`. Keep old keys while records or tokens still depend on them.

The DynamoDB table `caldav-mcp-prod-state` is provisioned at exactly 1 read and 1 write capacity unit, with no indexes and no autoscaling. The login page reads it before authentication, so a small burst of unauthenticated requests can exhaust it and make the service return 503. It is retained when the stack is deleted. Keys use the `caldav-mcp#` prefix, and runtime IAM enforces that prefix. The `expiresAt` TTL is only eventual cleanup; expiry is also checked on every read.

Lambda runs `nodejs26.x` on arm64 with 1024 MB, a 60 second timeout and 14 days of logs. No calendar data is retained except attachment copies staged in a private bucket for about one day, with eventual lifecycle cleanup. Each tool call reads iCloud when it needs to.

The download bucket belongs to the bootstrap stack. It blocks all public access, enforces bucket-owner object ownership, encrypts with SSE-S3 (AES256), refuses non-TLS requests, has no versioning and no CORS, and a lifecycle rule expires everything under `downloads/` after one day. S3 runs lifecycle rules about once a day, so a copy can last somewhat longer than 24 hours. Each download writes a new object under `downloads/v1/<hash of the account id>/<256 random bits>`, with no file name, event or account id in the key. The runtime role may only `PutObject` and `GetObject` under `downloads/`. Download links are presigned for at most five minutes, shorter if the signing credentials expire sooner. A link stays valid until it expires even if the grant is revoked; rolling back or disabling the tool stops new links only.

## Deployment and rollback

Deployment is enabled. The repository variable `DEPLOY_ENABLED` is `true`; the owner set it on 2026-11-11, so every push to `main` deploys. Pushes and pull requests to `main` and `develop` validate and build. The deploy job runs only on `main` and only when `DEPLOY_ENABLED` is `true`. The workflow never sets that variable itself. When it runs, it uses short-lived GitHub OIDC credentials and deploys the exact artifact the verify job built. The verify job has no AWS credentials. No long-lived AWS key is stored in GitHub. Actions are pinned by tag, not by commit, and the deploy job has no approval gate.

The public hostname is `caldav-mcp.rungie.com`. The template pins it as the only allowed value of `PublicDomainName`. `HostedZoneId` is the same existing zone wildduck-mcp uses.

The bootstrap stack creates the CloudFront distribution, two challenge-header policies, DNS records in the existing `rungie.com` zone, the artifact bucket, the attachment download bucket and its TLS-only policy, and two IAM roles. It needs the existing `GitHubOIDCProvider-Arn` and `CertificateAccepterLambda-Arn` exports. The distribution's origin is the `FunctionUrlOrigin` parameter, an existing Function URL origin without a trailing slash. The service stack imports the bootstrap exports `caldav-mcp-prod-public-origin` and `caldav-mcp-prod-download-bucket`. The CI deploy role has no rights on the download bucket; only the bootstrap stack, run by the owner, creates or changes it.

**The service stack imports `caldav-mcp-prod-download-bucket`**, so the owner must have updated the bootstrap stack (which adds the private download bucket) before a service deploy; the deploy fails until that export exists. Run step 1 below again (`bun run setup:deployment`; it updates the existing stack and keeps the stored `FunctionUrlOrigin`), or deploy `infra/bootstrap.yml` to `caldav-mcp-bootstrap` with `aws cloudformation deploy --region us-west-2 --stack-name caldav-mcp-bootstrap --template-file infra/bootstrap.yml --capabilities CAPABILITY_NAMED_IAM`. After a service deploy, `scripts/verify-deployment.mjs` checks that the function received `DOWNLOAD_BUCKET_NAME`.

First deployment, run once by the repository owner on a machine where `aws` (v2) and `gh` are already logged in and `bun` is installed. It follows the stages wildduck-mcp went through: roles and bucket first, then the service, then the distribution on the real Function URL.

The first deployment was carried out on 2026-11-11. The stacks `caldav-mcp-bootstrap` and `caldav-mcp-prod` exist in `us-west-2`. Step 1 and setting `DEPLOY_ENABLED` were done with equivalent individual commands, before `scripts/setup-deployment.sh` existed in the checkout. The procedure below is how to repeat it.

1. Run the one-time setup. Put the allowlist hashes (from `bun run apple-id-hash`) in the environment, never in a file:

   ```sh
   ALLOWED_APPLE_ID_HASHES='<hash>[,<hash>...]' bun run setup:deployment
   ```

   If `SERVERLESS_ACCESS_KEY` is not already a repository secret, export it too, or run from a terminal and `gh` will ask for it without echoing. Add `--dry-run` to see what would run. Re-running is safe.
2. When you are ready to deploy: `bun run setup:deployment -- --enable-deploy`
3. Release to `main` with the gitflow `postversion` flow (see "Branches and releases"). The deploy creates the service and its real Function URL. On the first CI deploy the deploy step succeeded and the live verification step failed, because the placeholder origin was still in place. Until step 4 has been run, the public hostname answers with CloudFront origin errors. After step 4, re-run the failed job: both steps then pass and the run turns green.
4. Point the distribution at the real Function URL and verify the live service: `bun run setup:deployment -- --finish`

The script (`scripts/setup-deployment.sh`) uses `us-west-2` and `hughescr/caldav-mcp` and nothing else. Step 1 creates or updates the `caldav-mcp-bootstrap` stack (a new stack gets a placeholder `FunctionUrlOrigin`; an existing one keeps its stored value), sets the repository variables from the stack outputs and from `ALLOWED_APPLE_ID_HASHES`, provisions the SSM keyring if it does not exist, and sets the `SERVERLESS_ACCESS_KEY` secret if it does not exist. It never touches `DEPLOY_ENABLED` unless given `--enable-deploy`. Secret values go to `gh` on stdin and are never printed. Step 4 reads the Function URL from the `caldav-mcp-prod` stack, strips the trailing slash, updates the bootstrap stack with it and runs `node scripts/verify-deployment.mjs`. Only `--finish` has run against real AWS and GitHub (2026-11-11). It succeeded: the bootstrap stack was updated to the real Function URL origin and `scripts/verify-deployment.mjs` passed. Step 1 and `--enable-deploy` of the script have only been run against stub `aws`, `gh` and `bun` programs.

Re-running step 1 keeps the stored `FunctionUrlOrigin`. Run `--finish` again if the Function URL is ever recreated.

If `aws` on your machine is a shell alias or wrapper that injects credentials (for example the 1Password shell plugin, `op plugin run -- aws`), a bash script and the AWS SDK do not see those credentials. `scripts/setup-deployment.sh` and `scripts/provision-auth-keyring.ts` then have no credentials. The keyring script was seen to hang for over two minutes in that state. In the same shell, run this first:

```sh
eval "$(aws configure export-credentials --format env)"
```

The OIDC trust pins the immutable owner and repository IDs and the `main` branch. Verify the subject format with `gh api repos/hughescr/caldav-mcp/actions/oidc/customization/sub`.

`bun run package` builds a package locally with placeholder settings and no AWS access. `bun run deploy` refuses missing settings. Never deploy placeholders with raw Serverless commands.

After a deployment, `scripts/verify-deployment.mjs` checks the live service. It checks the version, readiness, the Bearer and Basic challenge headers, discovery metadata, and that the live Lambda has a non-empty allowlist (its value is not printed). It then registers a throwaway client and cancels the login page, which exercises the gateway without logging in any account. It never sends a real Apple ID or password.

Rollback: use the published Lambda versions and the previous artifact. Restore the previous reviewed release and configuration, then verify health, version, discovery and readiness. Do not use `serverless remove` as a rollback. Keep the keyring keys that surviving records need. Rolling back the code does not undo changes already made to calendars. Rolling back to a release without consent records makes a client's superseded, unexpired grants work again, and that release refuses (with 503) the codes the newer build issued; never delete `consent` records by hand (see "One consent per client" in [docs/auth-design.md](docs/auth-design.md)). The table, the artifact bucket, the distribution, the header policies and the certificate are retained after stack deletion. The download bucket is not: it holds only disposable copies. A non-empty bucket blocks deletion of the bootstrap stack: CloudFormation cannot delete a bucket that holds any object, so the stack delete fails. The lifecycle rule is eventual (S3 runs it about once a day, and a new download can land at any time), so waiting does not guarantee an empty bucket. Stop new downloads, empty the bucket (`aws s3 rm s3://<bucket> --recursive`; it is unversioned), then delete the stack. Rolling the service back to a release without the download tool leaves the bucket and its export in place; that is harmless. Keep the ACM validation DNS records for renewal.

## Branches and releases

This repository uses gitflow, as wildduck-mcp does. Work happens on `develop`. `main` receives merges only for releases, through the `postversion` script, and deployments run from `main`. Tags are bare package versions. Set up git-flow with `bun run gitflow:init`. The release script (`scripts/postversion.sh`) refuses to run when untracked files exist. From a clean `develop`, run `bun pm version patch --no-git-tag-version`. The postversion script updates the lockfile, validates, commits, finishes the git-flow release and merges `main` back into `develop`. Nothing is pushed automatically. `bun run test:release` tries the release path in a disposable repository.
